### What 1.0.0 brings

#### Major Changes

- d204f8c: Xray 1.0, the first release of `@adrianeyre/xray`: the `xray` binary, the engine sidecar and the web app, in one package, for Windows, macOS and Linux. Install it with `pnpm add -g @adrianeyre/xray`, then run `xray doctor`, which checks Node.js 26.10.0, a .NET SDK 8 or later, and the engine.

  - `xray inspect <assembly> [--json]` summarizes a Managed Assembly's metadata: its name, version, target framework, architecture, entry point, output kind, references, how many types, methods and resources it defines, the PDB beside it and any sign of obfuscation. A Native Executable, or a file that is not a PE file, is rejected, saying why (exit code 3).
  - `xray reconstruct <assembly|folder> -o <dir> [--force] [--no-build] [--run] [--no-siblings] [--offline]` turns a Managed Assembly into a Recovered Solution: an SDK-style project for its original target framework, one C# file per type, its references resolved by the framework, NuGet packages, Sibling Assemblies and copied binaries, then builds it with `dotnet build` and classes it as a Full or Partial Reconstruction (exit code 4), printing a summary and writing `xray-report.json`, whose schema is documented and versioned (`schemaVersion` 1).
  - `xray ui [--port <n>]` serves the web UI on `127.0.0.1` only: drop an Assembly or a folder, or give a path, follow the Reconstruction live, browse the recovered C# and XAML, read the report, and download the Recovered Solution as a zip. Nothing leaves the machine but NuGet lookups and restores, which `--offline` turns off.

#### Minor Changes

- 4427926: `xray reconstruct` and `xray ui` reconstruct Assemblies for .NET Framework 2.0 and 3.5 and `netstandard`, on a best-effort basis, each into an SDK-style project for its own framework. An Assembly built before .NET Framework 4.0 records no `TargetFrameworkAttribute`, so its framework, `net20` or `net35`, is told from its CLR and what it references. `xray inspect` (`targetFramework.inferredFrom`, `targetFramework.support`) and `xray ui`'s inspect summary say how a framework was told and how far Xray supports it; a Reconstruction of an Assembly for a framework supported on a best-effort basis warns of it, on stderr, in `xray-report.json` (`warnings`) and in `xray ui`'s report. An array indexed from its end is decompiled as `values[values.Length - 1]`, not `values[^1]`, for a framework without `System.Index`, such as .NET Framework and .NET Standard 2.0, so it builds. An Assembly for .NET Framework 1.x is refused, saying no SDK-style project can target it.
- 89352ec: The web app's viewer highlights projects (`.csproj`) and `.resx` files as XML, as it does XAML, and solutions (`.sln`): their header, comments, keywords, quoted names and paths, GUIDs and version numbers. Any other file it shows as plain text, as before.
- a2aa3d7: `xray reconstruct` and `xray ui` copy an Assembly beside the input that a reference names, but that is a third party's (strong-named with another key than the input's) or, with `--no-siblings`, any, into the Recovered Solution's `Dependencies/`, and reference it with a `HintPath`, rather than reconstruct it. A reference nothing satisfies is an Unresolved Dependency, named, with why, which makes the Reconstruction Partial, built or not. `xray-report.json` (`dependencies`) records how every reference was resolved, and why; `xray reconstruct` counts them, and `xray ui` shows them as a table.
- d037568: `xray reconstruct` and `xray ui` read the `.deps.json` beside a .NET Core or .NET 5+ input, which says which version of which NuGet package each of its assemblies came from, and look a reference up in those packages first. A package named otherwise than its assembly (`CommandLineParser`'s `CommandLine.dll`) is now referenced as a package, and so is one whose assembly version many releases share (the AWS SDK for .NET's `3.3.0.0`), downloading only the version the app was built with rather than up to 10 that do not hold it. What the `.deps.json` says is still checked against the reference, and `xray-report.json` (`packages`) says when it named the package chosen.
- 7a62b55: `xray reconstruct` and `xray ui` reference each assembly a NuGet package holds as that package, with a `PackageReference`, rather than reconstruct it: matched by name, version and public key token, looked up in the global-packages cache, then on nuget.org. Of several versions holding the same assembly, the one holding the very file beside the input is chosen, else the highest, and `xray-report.json` (`packages`) says which and why. `--offline` makes no network calls: packages are looked up, and restored by `dotnet build`, only from the global-packages cache. Only package names and versions are ever sent to nuget.org.
- 2ea1297: `xray inspect`, `xray reconstruct` and `xray ui` say whether an Assembly is likely obfuscated, and why: an attribute a known obfuscator marks its output with, names an obfuscator gives rather than a programmer (unprintable, or mostly one or two characters long), or strings hidden behind decoders rather than written as literals. `xray inspect` gives each sign found (`obfuscation`); a Reconstruction of an obfuscated Assembly carries on, as it is, never deobfuscated, saying so in its summary, with a warning on stderr, in `xray-report.json` (`obfuscated`, each project's `obfuscation`, `warnings`) and in `xray ui`'s inspect summary and report.
- caeeaa3: `xray reconstruct` and `xray ui` decompile an Assembly, and each Sibling Assembly, with the PDB beside it, portable or Windows, when that PDB is the Assembly's own: locals keep the names they were given, and the source files are laid out as the original's were, each type declared in the file it was declared in. A PDB that is another build's, or cannot be read, is ignored with a warning, on stderr, in `xray-report.json` (`warnings`) and in `xray ui`'s report. `xray inspect` (`pdb`) says which PDB is beside an Assembly and whether it is its own.
- be55ea1: Recover embedded resources and `.resx`: every resource of an Assembly's manifest, and of its satellite assemblies beside it, is recovered into its project under its original logical name, public or private as it was, so the rebuilt Assembly's manifest names the same resources. A `.resources` file of strings, `byte[]`s and streams becomes a `.resx`, beside the type it is named after, a culture's beside the neutral one; any other resource is embedded as it is, with a warning for a `.resources` file kept so. `xray reconstruct` counts them in its summary, `xray-report.json` gives each in `solution.projects[].resources`, and `xray ui` shows them in its report.
- 0a2c9b4: `xray reconstruct` and `xray ui` reconstruct each Sibling Assembly an Assembly references, found beside it, into a project of its own in the same solution, wired with `ProjectReference`; `--no-siblings`, or turning it off in `xray ui`, leaves them be. Either takes a folder, reconstructing the application's Assembly in it. Two Assemblies of one name, and Assemblies that reference one another in a cycle, are reported in `xray-report.json` (`siblingProblems`) rather than stopping the Reconstruction.
- 137b721: Reconstruct Windows Forms apps, for .NET and .NET Framework, into projects that build on any OS: a project whose Assembly references Windows Forms uses it again (`UseWindowsForms`), for a Windows target framework where .NET 5 or later needs one, with `EnableWindowsTargeting`; each form is decompiled with the `InitializeComponent` its designer wrote, and its resources, its icon and images among them, are kept byte for byte, referencing `System.Resources.Extensions` where .NET Framework needs it to read them. The `ApplicationConfiguration` the Windows Forms source generator wrote is kept as decompiled. Off Windows, such an Assembly is decompiled with the reference assemblies of its framework, from the global-packages folder or, unless `--offline`, nuget.org, with a `reference-assemblies-not-found` warning where they are found in neither.
- de7dcea: Reconstruct WPF apps into projects that build on any OS: a project whose Assembly references WPF uses it again (`UseWPF`), for a Windows target framework where .NET 5 or later needs one, with `EnableWindowsTargeting`. The BAML of its WPF resources is decompiled back to XAML, with ILSpy's BAML decompiler, its resource dictionaries and styles among it, and an app's `Startup` and other events, each file listed as the `ApplicationDefinition` or a `Page` beside its code-behind, and every other file they held as a `Resource`; each class's code-behind leaves out what the markup compiler generates again from its XAML, so it compiles without a member declared twice. The report counts the WPF resources as recovered as `xaml`, and warns (`xaml-not-recovered`) where their BAML is kept as it is. The web app's viewer highlights XAML.

#### Patch Changes

- e95fce6: `xray reconstruct` and `xray ui` declare each `[GeneratedRegex]` method `partial`, as it was written, in types declared `partial`, and leave out what the regex source generator wrote of it (the method's body, its `[GeneratedCode]`, and the `Regex` and `Utilities` it declared file-scoped in `RegexGenerator.g.cs`), for the generator to write again as the Recovered Solution is built. Before, all of it was decompiled as ordinary code beside the attribute, and the generator refused the method (`SYSLIB1043`), so the Recovered Solution did not build. With a PDB, the generator's code no longer decides which file a type is laid out in.
- ea6ea6f: `xray reconstruct` and `xray ui` leave a reference to an assembly signed with one of Microsoft's keys to the target framework only where the framework provides it: where its reference assemblies (`Microsoft.NETCore.App.Ref`, `Microsoft.NETFramework.ReferenceAssemblies.*`, `NETStandard.Library`…), found in the .NET SDK's packs folder, the global-packages cache or, unless `--offline`, on nuget.org, hold an assembly of that name at that version or later. Any other is one of Microsoft's NuGet packages (`System.CommandLine`, `NuGet.Versioning`, `System.CodeDom`, `Microsoft.Extensions.*`, or `System.Collections.Immutable` 9.0 for .NET 8…), now referenced with a `PackageReference`, or else copied, never reconstructed as a Sibling Assembly; before, it was left to a framework that did not provide it, and the Recovered Solution did not build. `xray-report.json` (`dependencies[].reason`) says which reference assemblies hold each reference, or do not.
- b47e20b: `xray reconstruct` and `xray ui` decompile an Assembly's types on every processor at once, so a Reconstruction of an Assembly of about 2,000 types and 5 MB takes seconds rather than tens of them, excluding `dotnet build`: under 60 s even on one processor. Its progress still names each type as the engine starts on it, at least once a second, but types finish out of order, so how many are done may stay the same from one event to the next.
- 4601b92: `xray reconstruct` and `xray ui` parenthesize a query that ends the `select` or `group … by` clause a query continuation follows, as in `from g in parts select (from t in g select Parse(t)) into g where !g.Contains(null)`. Before, the decompiler wrote it without the parentheses, so C# read the `into g` as the inner query's (`CS1931`) and the clauses after it as reading the inner query's results (`CS1061`), and the Recovered Solution did not build.
- 13d2ba6: Run on Node.js 26 or later, rather than only 26.10.0: `engines.node` is now `>=26`, and `xray doctor` passes on any Node.js 26 or later.
